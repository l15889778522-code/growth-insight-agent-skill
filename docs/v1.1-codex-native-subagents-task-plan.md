## 1. 目标与边界

v1.1 的核心目标是把当前主要依赖提示词约束的七角色流程升级为：

> Codex 主任务负责编排，Codex 原生自定义子 Agent 负责各角色分析，确定性脚本负责状态、校验、审批绑定、查询执行、产物落盘和恢复。

必须实现：

1. 主任务是唯一编排器和唯一产物写入者。
2. 每个实际执行的业务角色对应一个可检查的 Codex 子 Agent 线程。
3. 七种角色能力继续保留，但按任务动态选择，不强制每次执行完整七阶段。
4. 每个角色完成后必须暂停；用户确认当前产物后，主任务才能启动下一角色。
5. Metrics 阶段允许用户新增、修改、删除指标，并对修订后的指标体系重新确认。
6. 保留真实 MySQL、SQLite 和后续数据库适配接口。
7. 数据库连接只读；任何真实查询都需要独立于角色确认的单独授权。
8. 状态、交接、审批、查询结果、指标血缘和图表必须机器可校验。
9. 中断后可从最后一个合法阶段边界恢复，重复确认不会重复启动角色。
10. 所有结论必须区分事实、计算结果、假设、推断和待验证项。

本版本明确不建设：

- DeepSeek 或其他外部模型 Provider。
- LangGraph、Agents SDK、CrewAI、AutoGen 等独立编排运行时。
- BI 平台、数据仓库或 ETL。
- 多用户权限管理后台。
- 无人值守的生产数据库自动分析。
- 多个子 Agent 并行写入同一份分析产物。

## 2. 架构决策

### 2.1 总体架构

```text
用户
  |
  v
Codex 主任务（Root Orchestrator）
  |-- 生成并校验 route-plan.json
  |-- 读取 run-state.json 决定唯一合法动作
  |-- 每次只启动一个已获授权的原生子 Agent
  |-- 等待、收集并关闭当前子 Agent
  |-- 调用确定性脚本校验和渲染产物
  |-- 展示阶段结果并等待用户确认
  |
  v
Codex 原生自定义子 Agent 线程
  |-- growth-business
  |-- growth-metrics
  |-- growth-sql
  |-- growth-insight
  |-- growth-visualization
  |-- growth-review
  `-- growth-report
  |
  v
单个结构化 JSON 响应
  |
  v
主任务与确定性脚本
  |-- JSON Schema 校验
  |-- Markdown 报告渲染
  |-- 状态、事件和审批原子写入
  |-- SQL 只读检查与获批后的查询执行
  `-- 指标、结果、洞察和图表血缘登记
  |
  v
awaiting_user_confirmation
```

架构固定为 Codex 原生能力，不再保留外部模型调用或第二套编排引擎。子 Agent 的可见线程、启动、等待、跟进和关闭均由 Codex 原生多 Agent 运行时完成。

### 2.2 单写入者原则

主任务是运行目录的唯一写入者。子 Agent 默认采用只读工作模式：

1. 读取原始请求、允许的数据文件和已批准的上游产物。
2. 完成当前角色分析。
3. 在最终响应中只返回一个符合阶段 Schema 的 JSON 对象。
4. 不直接修改 `run-state.json`、审批记录、其他角色产物或数据库。
5. 不直接执行真实 SQL。

主任务收到子 Agent 响应后：

1. 先保存原始响应，便于失败诊断。
2. 提取并校验 JSON。
3. 校验通过后渲染 `<stage>.md`。
4. 原子更新状态和事件日志。
5. 展示报告并结束当前回复，等待用户下一条确认消息。

这样可以避免并发写入、半份状态文件和子 Agent 越过审批门。Visualization 子 Agent 只生成图表规格，真实 PNG 或 HTML 由确定性渲染脚本生成。

### 2.3 原生自定义 Agent

七个角色继续使用独立 TOML，必须至少包含 Codex 官方要求的：

```toml
name = "growth-metrics"
description = "..."
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
...
"""
```

角色文件必须改为路由无关：

- 不再写死“第几个阶段”。
- 不再自行决定或启动下一角色。
- 不再写死固定输出文件编号。
- 只对当前角色职责和结构化输出负责。
- `recommended_next_stage` 只能是建议，最终路由由主任务决定。

子 Agent 继承当前 Codex 会话的实时权限设置。角色 TOML 中的 `sandbox_mode` 是最小权限默认值，不能替代主任务的查询确认和状态校验。

### 2.4 原生模型配置

v1.1 默认采用 `native-portable` 模型配置：

| 角色 | 模型策略 | 推理强度 | 原因 |
|---|---|---:|---|
| Business | 继承当前 Codex 原生模型 | `medium` | 业务范围和决策问题 |
| Metrics | 继承当前 Codex 原生模型 | `high` | 公式、粒度、维度和依赖 |
| SQL | 继承当前 Codex 原生模型 | `high` | Schema 映射和 SQL 风险 |
| Insight | 继承当前 Codex 原生模型 | `high` | 证据、归因假设和反证 |
| Visualization | 继承当前 Codex 原生模型 | `medium` | 图表规格和信息顺序 |
| Review | 继承当前 Codex 原生模型 | `high` | 一致性和证据审计 |
| Report | 继承当前 Codex 原生模型 | `high` | 决策优先的综合报告 |

选择“继承模型”作为默认值，是为了避免同一账号在不同 Codex 客户端、版本或可用模型集合不同时因硬编码模型名而无法启动。

同时保留可选 `native-explicit` 策略：

- 每个角色可在 TOML 中独立设置 Codex 当前可用的原生 `model`。
- Insight 和 Review 可在模型支持时提高到 `max`。
- 启动前必须验证模型与推理强度可用。
- 显式模型不可用时必须暂停并提示修改配置，禁止静默换成其他模型。
- 该策略直接使用各角色 TOML 的原生配置，不引入第二套 Agent 文件或模型路由器。

本版本不读取 `DEEPSEEK_API_KEY`，也不配置任何外部 `model_provider`。

### 2.5 Skill、Agent 安装与跨设备同步

仓库是 Skill、Agent 和确定性脚本的唯一配置源；`assets/custom-agents/*.toml` 是七个 Agent 的配置源。

安装支持两种目标：

1. 个人全局模式：Skill 安装到 `$HOME/.agents/skills/multi-agent-data-analysis-skill/`，Agent 安装到 `$CODEX_HOME/agents/`。
2. 项目测试模式：Skill 安装到测试项目的 `.agents/skills/`，Agent 安装到 `.codex/agents/`。

安装脚本必须：

- 校验七个 Agent 名称和必需字段。
- 输出源文件与目标文件的 SHA-256。
- 生成安装清单，便于检查版本是否一致。
- Skill 安装后从自身根目录解析脚本、Schema 和隔离 `.venv`，不依赖用户当前工作目录。
- 不覆盖名称冲突但内容不同的文件，除非用户显式指定 `-Force`。
- 提示安装或更新后重启 Codex 以重新加载 Agent。

另一台设备只需克隆同一 Git 仓库、运行 Skill 与 Agent 安装脚本并重启 Codex。数据库凭据和本地路径配置不进入 Git，需在目标设备单独配置。

自定义 Agent 新装或更新后设置一个明确的运行时重载检查点：

1. 记录待加载 Agent 文件的版本和 SHA-256。
2. 若当前任务尚未加载该版本，把开发进度记录为 `awaiting_codex_restart`。
3. 提示用户重启 Codex，并在同一仓库中回复 `恢复执行 v1.1`。
4. 重启后通过冒烟 Agent 返回的 `agent_contract_version` 验证新配置已经生效。
5. 该重启只恢复已确认的开发计划，不要求用户重新审批整个 v1.1 方案。

`awaiting_codex_restart` 只用于记录 v1.1 开发过程的技术检查点，不属于分析任务的 `run-state.json` 状态枚举。

### 2.6 子 Agent 生命周期

每次角色尝试对应一个独立、可见的原生子 Agent 线程：

1. 主任务从合法状态构造最小上下文。
2. 显式指定自定义 Agent 名称并启动。
3. 等待子 Agent 完成。
4. 保存原始返回，记录可获得的运行时线程标识和实际模型信息。
5. 校验结构化输出。
6. 必要时向当前线程发送一次定向纠正；若运行时不能继续该线程，则用同一角色创建一次修复尝试。
7. 校验通过后关闭已完成线程。

方案不依赖同一子 Agent 线程跨用户消息继续存在。用户要求修改时，主任务创建该角色的新 `attempt`，并把已批准版本与修改要求显式传入。

## 3. 工作流与人工确认

### 3.1 受控动态路由

保留七种角色能力，但按任务选择实际路径。主任务先生成 `route-plan.json`，展示建议路径，用户确认后才启动第一个角色。

| 任务类型 | 默认角色路径 | 必需前置输入 |
|---|---|---|
| 完整业务诊断 | Business -> Metrics -> SQL -> Insight -> Visualization -> Review -> Report | 业务问题；进入 SQL 前提供 Schema、数据字典或数据库连接 |
| 仅设计指标 | Business -> Metrics -> Review | 业务背景、分析目标或待衡量的问题 |
| 已有指标，生成 SQL | Metrics -> SQL -> Review | 已确认指标定义、Schema 和 SQL 方言 |
| 已有查询结果，分析原因 | Business -> Insight -> Visualization -> Review -> Report | 查询结果文件、字段说明和关键指标口径 |
| 仅做分析评审 | Review | 待评审的报告、SQL、指标或结果文件 |
| 仅生成最终汇报 | Review -> Report | 已完成的分析产物及其证据来源 |

`route-plan.json` 至少记录：

```text
route_id
route_revision
task_type
stages[]
required_inputs
provided_inputs
missing_inputs
fallback_route
user_adjustments
created_at
```

每个 `stages[]` 元素至少记录：

```text
stage_id
role
sequence
depends_on
required_inputs
expected_outputs
status
```

路由规则：

1. 用户可以在执行前增加、删除或调整角色顺序。
2. 缺少前置输入时，不得启动依赖该输入的角色。
3. 路由器应增加必要前置角色、请求用户补充，或采用明确标记能力边界的 `fallback_route`。
4. 用户已提供等价输入时可以跳过角色，但必须记录跳过依据。
5. 路由调整后增加 `route_revision`，旧确认不能批准新路由。
6. 每次只能有一个角色处于 `running`。
7. 简单任务不能因为 Skill 存在七个角色而被强制拉长。
8. 运行中因新证据、缺失数据或 Review 结果需要改路时，主任务必须生成新路由修订并回到 `awaiting_route_confirmation`。
9. 新路由确认不会批准任何尚未批准的角色产物；仍可复用且依赖未变化的已批准产物必须列入 `reused_approved_artifacts`，随新路由一并展示和确认。
10. 任何进入 Report 的路径都必须先经过 Review，且 Review 结果只能是 `PASS` 或 `PASS_WITH_RISKS`。
11. 当用户要求删除 Review 但仍要求最终报告时，路由校验必须拒绝该修改并说明依赖关系。

路由确认门只接受：

- `确认路由`
- `修改路由：...`
- `终止分析`

路由确认必须绑定 `route_revision` 和 `route-plan.json` 的 SHA-256。`继续` 只用于已展示的角色产物，不能模糊地批准一份新路由。

### 3.2 角色确认门

角色产物展示后，主任务只接受针对当前 `run_id + stage_id + artifact_revision` 的明确命令：

- `确认，进入下一步` 或 `继续`
- `修改：...`
- `补充：...`
- `重新生成当前阶段` 或 `重新生成这一阶段`
- `跳过当前阶段`
- `回退到：<角色>`
- `终止分析`

确认规则：

1. 原始分析请求不算阶段确认。
2. 早先阶段的确认不能复用于当前阶段。
3. 沉默、泛泛认可或其他任务中的确认不算批准。
4. 一条阶段确认最多授权一个下一角色。
5. 主任务必须在后续用户消息中收到确认，不能在展示产物的同一回复里继续启动下一角色。
6. 下游角色只能读取已批准产物的精确版本。
7. 最终 Report 通过校验后进入 `finalizing`；重建血缘、验证图表并生成运行摘要后，确定性 `finalize` 命令才提交 `completed`。
8. `跳过当前阶段` 会丢弃当前未批准产物并生成新路由修订；只有下游前置输入仍满足或已有等价输入时才允许跳过。

### 3.3 Metrics 人工编辑门

Metrics 阶段展示后支持：

- `新增指标：<定义>`
- `修改指标：<metric_id 或指标名>，<修改内容>`
- `删除指标：<metric_id 或指标名>`
- `重新生成当前阶段`
- `确认最终指标体系`

每个指标至少包含：

```text
metric_id
name
type
business_definition
formula
grain
dimensions
time_window
field_dependencies
status
source
owner
data_risks
version
```

指标状态为 `exploratory | candidate | official`。

用户编辑流程：

1. 主任务把编辑规范化为符合 `metric-edit.schema.json` 的 `add | modify | delete` 对象，并绑定当前 Metrics 产物哈希。
2. 以当前指标版本为基线，重新启动 Metrics 角色生成新修订。
3. 校验 Schema、`metric_id` 唯一性、字段依赖、公式冲突以及用户要求的字段是否被逐项落实。
4. 新修订展示给用户重新确认。
5. 未确认前不启动 SQL 或其他下游角色。
6. 修改已被下游使用的指标时，相关下游产物全部标记为 `stale`。

### 3.4 真实查询独立确认门

SQL 角色只设计和审查 SQL，不执行数据库查询。需要真实结果时采用两步授权：

1. 用户先确认 SQL 角色产物。
2. 主任务展示数据源非敏感标识、物理数据源 SHA-256 指纹、完整 SQL、SQL SHA-256、方言、超时和最大行数，并等待 `确认执行查询：<sql_sha256>`。

规则：

- 查询确认只授权该哈希对应的一次只读查询，不授权修改后的 SQL。
- SQL 内容、参数、数据源或限制发生变化时，原查询确认立即失效。
- 查询成功后，主任务保存结果与画像，再启动已由 SQL 阶段确认授权的下一角色。
- 用户拒绝查询时，可选择停止、提供结果文件，或继续“仅假设与验证方案”的 Insight 路径。
- 用户提供现成结果文件时不触发数据库查询确认，但必须记录文件哈希和字段画像。

### 3.5 Review 回退与上游修订

Review 返回 `FAIL` 时：

1. 不得启动 Report。
2. 必须指出最早需要修复的责任角色和具体失败项。
3. 主任务展示建议回退路径并等待用户确认。
4. 回退后创建目标角色的新尝试，不覆盖历史产物。
5. 依赖旧版本的下游产物标记为 `stale`，必须重新生成或重新评审。

Review 返回 `PASS_WITH_RISKS` 时，风险必须原样进入 Report，不能被静默删除。

### 3.6 停止与恢复

- `终止分析` 把运行标记为 `stopped`，不再启动子 Agent。
- `恢复分析：<run_id>` 先执行一致性检查，再回到最后一个合法等待状态。
- 如果只有一个可恢复运行，主任务可以建议该 `run_id`，但不得在无用户指令时自动推进。
- 正在运行的子 Agent 被中断时，只能重试当前角色，不能假定其未落盘工作已完成。

## 4. 状态机与机器交接

### 4.1 运行目录

动态路由不再依赖固定的七个文件名。每次运行使用：

```text
multi-agent-data-analysis-runs/<run_id>/
  request.json
  route-plan.json
  run-state.json
  events.jsonl
  approvals.jsonl
  stages/
    <sequence>-<role>/
      attempt-<n>/
        raw-response.txt
        stage.json
        stage.md
        validation.json
  data/
    query.sql
    query-manifest.json
    result.csv
    result-profile.json
  lineage/
    metric-lineage.json
  charts/
    chart-specs.json
    *.png
    *.html
  final/
    final-report.md
```

完整七角色路径可以额外生成旧版文件名映射，便于兼容现有测试，但旧文件名不再作为状态事实来源。

### 4.2 运行状态

`run-state.json` 至少包含：

```text
schema_version
run_id
revision
status
runtime.kind
runtime.model_policy
runtime.agent_config_hashes
runtime.resolved_models
route_id
route_revision
route_sha256
current_stage
pending_stage
stages
approved_artifacts
pending_approval
pending_query
pending_metric_edit
artifacts
data_source
```

- 每次状态变化增加 `revision`。
- 使用追加式 `events.jsonl` 保存不可变事件。
- 状态只保存当前投影，历史以事件和版本化产物为准。
- 恢复时校验状态、事件、审批和产物哈希是否一致。

### 4.3 审批绑定与幂等

所有确认采用统一审批对象，每条记录至少包含：

```text
approval_id
approval_type
run_id
route_revision
subject_id
subject_revision
subject_sha256
action
user_text
created_at
idempotency_key
```

`approval_type` 为 `route | stage | query | rollback`：

- 路由审批的 `subject_id` 是 `route_id`，哈希绑定 `route-plan.json`。
- 阶段审批的 `subject_id` 是 `stage_id`，哈希绑定当前 `stage.json`。
- 查询审批的 `subject_id` 是查询 ID，哈希绑定完整 SQL 与执行限制。
- 回退审批的 `subject_id` 是目标阶段 ID，哈希绑定回退计划。

同一 `idempotency_key` 重复提交时返回已有结果，不得再次启动子 Agent。对象哈希或对象修订变化后，旧审批自动失效。

路由修订变化时：

- 旧路由审批、查询审批和回退审批失效。
- 旧阶段审批默认不承接。
- 只有阶段节点、输入依赖哈希和产物哈希均未变化，且新路由的 `reused_approved_artifacts` 明确列出该产物时，才写入 `approval_carried_forward` 事件。
- 用户确认新路由后，该承接事件才生效；其余旧阶段产物标记为 `stale` 或保持历史只读状态。

查询审批额外绑定：

```text
query_sha256
data_source_id
data_source_fingerprint
dialect
timeout_seconds
max_rows
max_result_bytes
```

### 4.4 机器可校验交接

子 Agent 最终响应只能包含一个 JSON 对象。公共字段至少包括：

```text

stage_id
role

summary
confirmed_decisions
conflicts
facts
calculations
assumptions
hypotheses

data_artifacts

```

角色专属内容放在 `role_payload`，并由对应阶段 Schema 校验。

`stage_status` 只能是 `PASS | PASS_WITH_RISKS | BLOCKED | FAIL`。下游角色不得静默修改已批准的 `confirmed_decisions`；发现冲突时必须写入 `conflicts`，并在冲突影响正确性时返回 `BLOCKED`。主任务随后提出回到责任角色或请求用户裁决的路径。

只有以下条件全部满足，当前阶段才可以展示给用户确认：

1. 原生子 Agent 正常结束。
2. 响应中可提取唯一 JSON 对象。
3. JSON 通过公共 Schema 和角色 Schema。
4. 所有输入引用都指向已批准产物。
5. 所有数据、SQL、指标和图表引用都能解析到真实文件或明确的待生成项。
6. Markdown 成功渲染。
7. JSON、Markdown 和校验报告已落盘并完成哈希登记。
8. 状态成功转为 `awaiting_user_confirmation`。

校验失败时只允许一次定向纠正。再次失败则把当前尝试标记为 `failed` 并暂停，不得启动下游角色。

### 4.5 恢复规则

恢复顺序：

1. 获取运行锁。
2. 校验 `run-state.json` 的 Schema。
3. 重放并核对 `events.jsonl`。
4. 校验最后已批准产物的 SHA-256。
5. 检查是否存在未完成或重复的 Agent 尝试。
6. 恢复到最后一个合法阶段边界。
7. 向用户展示当前状态和唯一允许的下一步。

v1.1 保证阶段边界恢复，不承诺恢复子 Agent 正在生成中的中间推理或工具调用。

## 5. 数据库、血缘与图表闭环

### 5.1 数据库适配

v1.1 必须继续支持：

- mock schema，用于无真实数据库时的演示和测试。
- 用户上传的 Schema、数据字典、样例数据或查询结果文件。
- MySQL 只读连接。
- SQLite 只读连接。
- 通过统一连接接口扩展其他数据库。
- 使用环境变量或本地忽略文件提供凭据。
- Schema 检查和连接测试不泄露密码。

数据库适配接口至少统一：

```text
test_connection
inspect_schema
execute_readonly_query
quote_identifier
normalize_type
```

SQLite 端到端测试必须始终可运行。MySQL 必须完成连接器契约测试，并在一次性测试实例或用户提供的只读测试库上完成真实集成测试后，才能把 MySQL 支持标记为完整通过。

### 5.2 SQL 安全

真实查询前必须同时满足：

1. SQL 通过 AST 或可靠解析器的只读校验，不能只依赖关键字字符串匹配。
2. 只允许 `SELECT`、`WITH`、`SHOW`、`DESCRIBE` 和 `EXPLAIN` 等明确只读语句。
3. 阻止多语句、注释绕过和写操作。
4. 数据库账号本身具备只读权限。
5. 设置超时、最大行数和结果大小限制。
6. 当前查询哈希已获得用户单独确认。
7. 在不改变查询语义时安全注入或收紧 `LIMIT`；无法安全改写时拒绝自动改写并要求人工确认。
8. 对可能全表扫描或高成本的查询先运行 `EXPLAIN` 或给出扫描风险，不把“只读”误判为“低风险”。

SQL 子 Agent 不持有“查询已批准”的判断权。查询只由主任务调用确定性脚本执行。

### 5.3 查询产物

真实查询后必须生成：

```text
data/query.sql
data/query-manifest.json
data/result.csv
data/result-profile.json
```

查询清单至少记录：

- 数据源类型和非敏感标识
- SQL SHA-256
- SQL 方言
- 执行时间与耗时
- 超时和最大行数
- 实际返回行数
- 字段、类型和空值统计
- 结果文件 SHA-256
- 是否截断或抽样
- 数据质量告警

Insight 只能把查询结果或用户提供的结果文件作为观测证据。没有结果时，只能输出假设和验证方案。

### 5.4 指标血缘

每个指标使用稳定 `metric_id`，并贯穿：

```text
metric definition
-> SQL expression
-> query result column
-> insight evidence
-> chart encoding
-> final recommendation
```

Review 必须检查关键指标链路是否完整，并报告断点。上游指标修订后，引用旧版本的 SQL、洞察、图表和报告必须变为 `stale`。

### 5.5 真实图表

Visualization 子 Agent 输出结构化图表规格。确定性脚本负责生成真实 PNG 和可选 HTML：

1. 每个图表引用 `metric_id`、结果文件、字段、过滤条件和聚合粒度。
2. 无可用数据时只保留规格，并标记 `blocked_by_missing_data`。
3. 不得用虚构数据生成看似真实的图表。
4. Review 校验图表、数据和结论一致性。
5. 图表渲染失败时保留规格与错误报告，不得把空白图表标记为成功。

### 5.6 运行依赖

实现必须声明并预检运行依赖，不能只在脚本报 `ImportError` 后让用户猜测安装项：

```text
requirements.txt
  jsonschema
  sqlglot
  pymysql
  matplotlib
  plotly

requirements-dev.txt
  pytest
  coverage
```

实际文件使用经过测试的兼容版本范围。预检脚本必须报告 Python 版本、缺失包和已加载版本，但不能自动更改用户的全局 Python 环境；安装命令由用户显式执行或在项目虚拟环境中执行。

## 6. 个人工作流的运行安全

本 Skill 用于个人工作流，不引入企业法务、数据合规审批、PII 分类或强制数据外发确认。保留以下技术保护：

1. 模型使用当前 Codex 登录和原生运行时，不保存额外模型 API Key。
2. 数据库凭据只从环境变量或本地忽略配置读取，不写入 Git、报告或日志。
3. 日志和异常不得输出数据库密码、Authorization Header 或其他完整凭据。
4. 子 Agent 默认只读；主任务和确定性脚本是唯一产物写入路径。
5. 数据库连接保持只读，真实查询必须绑定独立用户确认。
6. 默认日志记录 Agent、模型、推理强度、耗时、状态、审批和产物哈希。
7. Token 使用量仅在 Codex 运行时明确提供时记录；不可获得时写入 `null` 和原因，禁止估算后冒充实测。
8. 是否保存完整 Prompt 由用户配置，默认不保存。
9. 子 Agent 失败、超时或输出不完整时保留可诊断错误，但不泄露凭据。
10. 数据文件、查询结果和数据库文本字段中的指令性内容一律视为数据，不能覆盖主任务、Skill 或角色指令。

具体文件名可在实施时按现有代码风格微调，但不得引入外部模型运行时，也不得扩大到 BI、数仓或平台建设。

## 9. 全局完成标准

v1.1 只有在以下条件全部满足时才算完成：

- `AC-01`：所有角色均通过 Codex 原生自定义子 Agent 运行，不调用 DeepSeek 或其他外部模型 Provider。
- `AC-02`：每个实际执行角色在 Codex 界面中有独立可检查线程，不由主任务模拟。
- `AC-03`：主任务是唯一编排器和运行产物写入者。
- `AC-04`：角色结束后必须在后续用户消息中获得确认，才能启动下一角色。
- `AC-05`：指标可由用户增删改，并保留修订、审批和下游失效记录。
- `AC-06`：路由可按任务裁剪，且缺少前置输入时不会误启下游角色。
- `AC-07`：状态、路由、审批、交接和阶段输出均通过 JSON Schema 校验。
- `AC-08`：中断后可恢复，重复确认不会重复启动角色。
- `AC-09`：SQL 阶段确认与真实查询确认相互独立，查询审批绑定 SQL 哈希。
- `AC-10`：MySQL 和 SQLite 的真实只读接口保留，写操作始终被阻止。
- `AC-11`：SQL、结果、指标、洞察、图表和最终建议形成可追溯链路。
- `AC-12`：缺少真实结果时不生成伪造结论或伪造图表。
- `AC-13`：Agent 配置、数据库凭据和日志满足个人工作流的技术安全要求。
- `AC-14`：另一台设备可以通过 Git 仓库、依赖清单和安装脚本复现 Agent 配置与运行环境。
- `AC-15`：自动化评测可比较单 Agent、v1.0 和 v1.1。

### 11.2 本次审查补齐的问题

相较上一版方案，本版已经补齐：

1. 移除 DeepSeek 直连、Stage Runner 和外部模型降级分支。
2. 明确原生子 Agent 的配置来源、安装位置、模型继承和可见线程生命周期。
3. 增加单写入者原则，避免七个子 Agent 直接竞争运行产物。
4. 将固定文件编号改为适配动态路由的阶段与尝试目录。
5. 增加审批对产物哈希、路由修订和幂等键的绑定。
6. 增加上游修订后的下游 `stale` 传播。
7. 把 SQL 阶段确认和真实查询确认拆成两个独立门。
8. 明确默认模型配置在不同 Codex 设备间的可移植策略。
9. 修正评测基线，避免“Codex 原生多 Agent”同时作为基线和候选方案。
10. 对 Token 等运行时不一定提供的数据定义了不可获得时的真实记录方式。
11. 增加 Agent 更新后的 Codex 重启与恢复检查点。
12. 增加 SQL AST、MySQL 和图表所需的依赖声明与预检。
13. 增加运行中重新路由的确认规则。
14. 明确 MySQL 支持必须通过真实只读集成测试，不能只用 Mock 宣称完成。
15. 保留阶段跳过、mock schema 和上传 Schema/结果文件等 v1.0 能力。
16. 补充安全 `LIMIT`、`EXPLAIN` 和高扫描风险控制。
17. 将路由、阶段、查询和回退确认统一为可校验、可幂等的审批对象。
18. 明确 Review 是 Report 的强制前置，并增加跨角色冲突的阻断与回退规则。

## 12. 已知限制

- 原生子 Agent 的线程展示位置和可用控制会随 Codex 客户端版本变化，但角色线程本身必须可检查。
- 子 Agent 会继承父会话的实时权限设置，因此敏感动作仍由主任务状态机和确定性脚本控制。
- v1.1 只保证阶段边界恢复，不恢复子 Agent 正在生成中的中间状态。
- 自定义 Agent 安装或更新后通常需要重启 Codex 才能重新加载。
- 显式原生模型和 `max` 推理强度取决于账号、客户端和模型可用性；默认继承策略用于降低该风险。
- Codex 若不提供每个子 Agent 的精确 Token 数据，评测只能将该字段标记为不可获得，不能伪造成本估算。
- 严格串行和逐角色确认会增加耗时与 Token，但这是本 Skill 可审计和可控制的核心。
- v1.1 首先保证 MySQL 和 SQLite；其他数据库通过统一适配接口后续增加。
