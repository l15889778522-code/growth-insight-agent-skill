## 2. 本轮测试结论

### 2.1 总体判断

- 作为首次完整流程联调：`有条件通过`。
- 作为当前 v1.2 正式验收：`不通过`。
- 作为可以直接支撑正式业务决策的分析：`不达标`。

### 2.2 已经证明的能力

- 七个专业角色可以按顺序执行并产生最终阶段报告。
- 路由确认、阶段确认和查询确认已经存在。
- SQL Agent 没有直接访问数据库，真实查询在用户确认后执行。

## 3. 问题总清单

问题状态使用以下定义：

| 状态 | 含义 |
|---|---|
| `P0` | 不修复就不能进行下一轮正式验收或发布 |
| `P1` | 严重影响结果可信度、用户决策或流程正确性 |
| `P2` | 影响效率、可维护性或体验，但不一定阻止运行 |
| `DEFERRED` | 已记录，暂不属于本轮范围 |

### 3.1 P0：运行合同版本未锁定

现象：

- 本次运行摘要的 `schema_version` 是 `1.1`。
- 七份最终阶段报告的 `agent_contract_version` 是 `1.1`。
- 路由、审批、查询和结果产物也属于 1.1 格式。
- 当前项目 `VERSION` 和目标运行合同是 `1.2`。

风险：

- 旧安装副本或旧运行器可能被误认为当前版本。
- 1.1 允许的行为可能绕过 1.2 的新约束。
- 测试报告看起来完成，但不能证明当前代码版本有效。

改进要求：

1. `run init` 时读取当前 Skill 的合同版本。
2. 运行、路由、阶段、审批、查询、血缘和报告全部校验版本一致。
3. 发现 1.1/1.2 混用时立即停止，不生成 `completed`。
4. 迁移旧运行时必须显式执行迁移命令并留下迁移事件。
5. 测试报告必须同时记录 Skill 源码提交号、安装路径和合同版本。

验收标准：

- 新建运行的全部 JSON 和 Markdown 产物为 `1.2`。
- 注入一个 1.1 阶段产物时，Review 和 finalize 必须拒绝运行。
- 旧 v1.1 fixture 只能通过显式兼容测试，不能混入 v1.2 正常运行。

### 3.2 P0：查询结果证据没有闭环

现象：

- 5 条 SQL 有审批记录和执行事件。
- 正式 `query-manifest/result/profile` 目录只完整保留了 `behavior_record_completeness`。
- 其他指标主要通过 `observed-metrics.json` 提供结果。
- `observed-metrics.json` 的 artifact 类型是 `user_result`，不是独立的 `query_result`。

风险：

- 无法独立重算每个指标。
- Insight、Review 和 Report 可能引用了没有正式结果文件支持的数值。
- 查询执行成功不等于查询结果已被安全发布。

改进要求：

每个指标都必须拥有独立的不可变查询目录：

```text
data/queries/<query_id>/revision-<n>/
  query.sql
  query-request.json
  approval.json
  result/query-manifest.json
  result/result.csv
  result/result-profile.json
```

每个结果必须包含：

- 对应 `metric_id` 和 `metric_revision`；
- 对应 `query_id` 和 `query_revision`；
- 执行时使用的 SQL 哈希；
- 审批哈希；
- 数据源指纹；
- 结果文件哈希；
- 结果列和单位；
- 分子、分母、cohort 数量和时间范围。

验收标准：

- 5 个指标对应 5 个正式查询结果目录。
- 删除任意一个结果文件后，Review 或 Report 必须被阻止。
- Report 可以从结果文件重新计算所有展示数值。

### 3.3 P0：SQL 哈希缺少唯一规范

现象：

- `observed-metrics.json` 记录的 SQL 哈希与 `data/queries/` 下对应 SQL 文件的 SHA-256 不一致。
- 当前没有清楚说明哈希是否基于去空格、格式化或其他标准化 SQL。

风险：

- 用户批准的 SQL 与实际执行的 SQL 可能无法独立确认是同一份。
- 以后无法准确判断查询结果属于哪一版 SQL。

改进要求：

1. 保存原始 SQL 和 canonical SQL。
2. 记录 canonicalization 规则版本。
3. 审批、执行、结果和报告全部只引用 canonical SQL 哈希。
4. 原始 SQL 变化或 canonicalization 规则变化时，必须生成新 revision。

验收标准：

- 审批文件中的 SQL 哈希可以由仓库保存的 canonical SQL 重新计算得到。
- 同一 query revision 不允许出现多个有效 SQL 哈希。

### 3.4 P0：Review 发现 P1 问题后仍然放行

现象：

Review 发现了 activation cohort、D7 时区、数据过滤、结果 manifest 和图表可比性等严重问题，但最终仍然是：

```text
decision = PASS_WITH_RISKS
required_fixes = []
rollback = null
```

风险：

- 高优先级问题被包装成普通风险。
- Report 可以在关键证据不完整时生成。
- 用户容易把“流程完成”理解为“结论可靠”。

改进要求：

- P0/P1 finding 必须产生 `FAIL`。
- 结果缺失、血缘断裂、关键指标未映射时必须 `FAIL`。
- `FAIL` 必须绑定回退阶段、修复要求和旧产物哈希。
- 未完成回退前，Report 必须保持 `BLOCKED`。
- 只有全部 P1 问题关闭后，Review 才能 `PASS`。

验收标准：

1. 故意删除一个 query result。
2. 运行 Review。
3. 结果必须是 `FAIL`。
4. 生成合法 rollback plan。
5. 修复并重新审批后，旧 Review 和旧 Report 不能继续被引用。

### 3.5 P1：业务问题太宽，路由直接进入完整流程

现象：

用户只说“分析用户行为”，但系统直接采用七阶段完整路线。Business Agent 已经发现缺少明确决策场景，流程仍然继续。

风险：

- 指标容易变成通用指标集合。
- SQL、图表和报告无法围绕一个具体决策组织。
- 简单问题也会消耗完整流程和模型额度。

改进要求：

- 根任务先识别业务问题类型。
- 如果缺少决策场景，先让用户选择或补充目标。
- 为完整分析、指标设计、已有 SQL、已有结果、只检查 SQL、只做 Review 提供确定性短路线。
- 路由确认页面必须说明：为什么推荐这条路线、会跳过哪些角色、预计需要哪些输入。

验收标准：

- 同一输入能够稳定生成同一预设路线。
- “只设计指标”不会启动 SQL、Insight、Visualization 或 Report。
- “已有结果分析”不会重复执行数据库查询。

### 3.6 P1：指标口径仍有临时假设

已发现的问题：

- `activation_rate` 没有充分排除尚未成熟的用户 cohort。
- `d7_retention_rate` 使用日历日逻辑，时区未确认。
- `engaged_user_rate` 的行为范围没有经过业务确认。
- follow 行为只计算 follower 侧。
- `behavior_record_completeness` 是数据质量指标，不应与用户行为 KPI 混为一类。

改进要求：

- 每个指标必须明确“可用于什么决策”和“不能用于什么决策”。
- 每个比例必须保存分子、分母、cohort 数、成熟度和数据截止时间。
- 未成熟 cohort 必须标记为 `not_ready`，不能直接转成 0。
- 业务行为指标和数据质量指标分开确认、分开展示。
- Metrics workbench 中要能人工修改名称、定义、公式、窗口、粒度、字段和适用条件。

### 3.7 P1：SQL 安全通过，但扫描成本不足

已发现的问题：

- 查询多为全表扫描。
- `LIMIT 1` 限制了返回行数，但没有限制底层扫描成本。
- 缺少 EXPLAIN 或等价成本检查。

改进要求：

- 没有时间范围的查询默认需要额外确认。
- 执行前运行 EXPLAIN 或成本估算。
- 增加最大扫描行数和最大执行时间。
- 失败时记录“安全拒绝”还是“性能拒绝”。
- 对大表优先要求分区、索引或明确查询范围。

### 3.8 P1：重试和状态机诊断信息不完整

已发现的问题：

- 多个失败尝试的 `validation.json` 仍显示 `valid=true`。
- 验证失败原因未完整写入结构化验证文件。
- `revision_requested` 没有稳定记录具体失败字段。
- 没有清晰区分 Agent 阻塞、数据库不可用、合同错误和业务输入不足。

改进要求：

- 每次失败都保存失败类别、失败原因、无效字段、责任阶段和是否允许重试。
- 区分自动修复、用户补充信息和必须终止三种处理方式。
- 设置合理的重试上限，超过上限必须暂停并说明原因。
- 失败阶段不能让下游误读旧的批准产物。
- 中断恢复测试要区分进程中断、数据库断开、Agent 未返回和文件短写。

### 3.9 P1：血缘引用可能读取旧 revision

现象：

- Review 使用的 lineage artifact 哈希与最终最新 lineage 修订不一致。
- lineage 文件已经记录部分指标缺少结果列和图表映射，但下游仍可继续。

改进要求：

- 每次启动 Review 前重新生成并冻结 Review input bundle。
- Review 只能读取 bundle 中的精确路径和 SHA-256。
- 最新指针变化后，旧 Review 输入自动失效。
- Report 必须继承通过 Review 的同一个 input bundle。

### 3.10 P1：图表技术上成功，但业务表达不足

已发现的问题：

- 活跃用户图只有单个柱子，缺少时间范围和值标签。
- 比例图把激活率、D7 留存率、互动率和完整性放在一起比较。
- Y 轴是 0 到 1，没有百分比格式。
- 0 值柱子不可见，用户可能误认为没有数据。
- 图表来源是汇总 CSV，不是正式 query result。

改进要求：

- 图表必须显示标题、时间范围、单位、数值标签和数据状态。
- 比例统一使用百分比，并显示分子/分母或 cohort 数量。
- 业务行为指标与数据质量指标分开绘图。
- 0、缺失、未成熟和未执行必须使用不同状态。
- 图表只能引用当前有效的 query result artifact。

## 4. 新增核心要求：阶段报告必须适合非技术用户阅读

### 4.1 当前可读性问题

现有阶段报告偏向 Agent 交接和开发审计，存在以下问题：

- 直接使用 `artifact_id`、SHA-256、schema、lineage、cohort、denominator 等术语。
- 结论、风险、技术细节和下一步混在一起。
- SQL 阶段先展示代码，用户不容易知道这条查询要回答什么。
- Metrics 阶段公式较多，但没有用通俗语言解释指标代表什么。
- Review 阶段列出很多 finding，但没有先说明“这份分析现在能不能用”。
- Report 阶段虽然比较谨慎，但普通用户仍需要理解数据血缘和统计限制后才能读懂。

### 4.2 可读性目标

每个阶段的报告必须先让普通用户回答五个问题：

1. 这一阶段做了什么？
2. 得到了什么结论？
3. 这些结论有多可信？
4. 现在有什么风险或缺失？
5. 我需要确认什么，下一步会发生什么？

用户不需要理解代码、数据库表名或哈希值，也应该能完成当前阶段确认。

### 4.3 统一报告结构

用户已确认：保留内部 `role_payload`，不删除业务含义和确认等栏目；用户阅读的报告必须是文字报告，不展示代码格式。每份阶段报告只整理当前 Agent 返回的内容，不拼接上游完整报告、不由根任务补写新的业务结论。最终报告是 Report Agent 自己的汇总。

阶段报告采用以下结构：

1. 一句话结论：用普通中文说明当前结果。
2. 这对你的业务意味着什么：说明本阶段内容可以支持什么判断。
3. 本阶段完成了什么：按当前角色展示专属内容，如业务范围、指标定义、查询目的、洞察、图表计划或复核问题。
4. 关键发现：保留当前角色报告的事实，不为压缩篇幅而丢失重要结论。
5. 需要注意的地方：保留全部风险、冲突和必要限制。
6. 需要你确认的内容：说明当前结果、缺少信息和建议下一角色；未通过或阻塞时明确不能批准。
7. 补充说明：仅在当前 Agent 提供时展示确认决策、分析前提、待验证判断和计算说明。
8. 技术详情：以中文说明和普通表格展示运行编号、文件位置、证据和完整性校验码。

技术详情仍然保留在业务内容之后，但不直接打印 JSON 或 SQL 代码。原始 SQL、机器校验字段和完整结构化内容继续保存在不可变的运行产物中。报告渲染只负责展示，不改变内部合同、证据哈希或审批规则。

### 4.4 面向普通用户的语言规则

- 第一次出现技术词时，先给中文解释，再保留英文原词。
- 使用“参与活动的用户数”，不要只写 `active_users`。
- 使用“计算分母”，并在括号中说明“作为比较基准的用户总数”，不要只写 denominator。
- 使用“数据还没有覆盖完整的第 7 天”，不要只写 right-censoring。
- 使用“这只是数据字段填写完整，不代表用户行为完整”，解释 completeness。
- 使用“暂时不能判断”，不要使用模糊的“存在不确定性”作为唯一说明。
- 一句话只表达一个判断。
- 每段不超过四行，复杂内容拆成表格。
- 不在确认提示中要求用户理解 SHA-256；哈希只作为括号内的审计编号展示。
- 文字报告说明查询目的、范围、计算粒度、比较基准和限制，不直接展开 SQL；准确查询语句仍保存在内部交接和查询文件中。
- 不使用代码块、行内代码样式或原始 JSON 展示任何角色的工作成果。
- 字段名称转换为中文标签，状态转换为可理解的结果；没有新证据时不能由渲染器编造业务判断。

### 4.5 七个阶段的可读性要求

| 阶段 | 报告必须先回答的问题 |
|---|---|
| Business | 我们到底要解决什么业务问题？这次不分析什么？ |
| Metrics | 建议关注哪些指标？每个指标用大白话是什么意思？ |
| SQL | 每条查询想回答什么？读了哪些数据？是否只读？ |
| Insight | 数据实际说明了什么？哪些只是可能原因？ |
| Visualization | 这张图应该怎么看？最重要的变化是什么？ |
| Review | 这份分析能不能使用？必须先修什么？ |
| Report | 最终结论是什么？下一步建议做什么？ |

### 4.6 阶段确认摘要

每次等待用户确认时，只在对话主体展示：

```text
本阶段结论：
发生的变化：
主要风险：
缺少的信息：
下一步将启动：
你可以确认、修改或回退到：
```

文件路径、哈希、完整 SQL 和原始 Agent 响应保留在运行目录中，只有用户需要时再展示。

### 4.7 可读性验收标准

阶段报告完成后，由没有代码经验的读者进行人工走查。满足以下条件才算通过：

- 读者能用一句话复述本阶段结论。
- 读者能指出当前最大的风险。
- 读者能知道是否需要确认或修改。
- 读者不需要阅读 SQL 或 JSON 才能完成确认。
- 报告首页不出现未解释的英文缩写或内部字段名。
- 技术详情与业务结论可以分开阅读。
- Report 的第一屏包含结论、证据状态、主要限制和下一步建议。
- 七种角色的报告都不直接打印 `role_payload` 或 JSON；原始数据在渲染前后完全相同。
- 嵌套的证据引用仍可以在技术详情或原始记录中找到，不因文字化而丢失。
- 风险超过五条时不会被静默截断，失败阶段不会提示用户直接批准。

### 10.3 双模式设计

增加显式运行模式，运行开始后写入状态并绑定路由版本；模式变化必须重新确认路线。

#### 个人模式 `personal`

作为默认模式：

- 面向日常分析和个人决策。
- 使用最短可回答路线，但七个角色配置始终保留；需要完整分析时仍按顺序运行全部七个角色。
- 默认采用关键确认门，不在每个低风险阶段停顿。
- 普通文字总结由根任务完成；只有用户需要正式综合报告时才调用 Report Agent。
- Visualization Agent 仅在用户需要图表时调用。
- 保留 SQL 执行确认、只读校验、证据解析、Review 阻断和中断恢复。

#### 严格模式 `strict`

保留当前受控流程：

- 每阶段人工确认。
- 完整 Agent 回执、不可变修订、事件哈希链和执行审计。
- 独立 Review 和按路线选择的 Report Agent。
- 适用于正式汇报、重要归因、复杂 SQL 和用户主动要求完整审计的任务。

严格模式默认隐藏在高级选项中，必须保持兼容；个人模式不能覆盖或破坏已有 v1.2 运行。

### 10.4 可配置确认策略

增加三种确认策略：

| 策略 | 用途 | 行为 |
|---|---|---|
| `key-gates` | 个人模式默认 | 只在路线与指标、SQL 与查询执行、最终结论处确认 |
| `every-stage` | 严格模式 | 保持每个角色产物逐阶段确认 |
| `test-auto` | 隔离测试 | 路线一次确认后自动完成非破坏性阶段；真实数据库查询仍必须单独确认 |

个人模式的确认目标：

1. 用户先看到推荐路线并确认是否采用。
2. 指标发生新增、修改或删除时，确认最终指标体系。
3. 执行数据库查询前，确认 SQL、数据范围、限制条件和准确查询哈希。
4. 正式报告或重要归因分析完成后，再确认最终交付物。

每个阶段仍生成可读报告和内部产物。低风险阶段可以自动继续，但不能把未批准指标、SQL 或查询结果传给下游。若一次阶段内部启动两个并行 Agent，用户只确认合并后的阶段结果。

### 10.5 按需角色和推荐路线

七个角色配置继续保留，根据任务选择是否运行；完整分析不跳过角色，主要阶段始终串行：

| 任务 | 个人模式默认路线 |
|---|---|
| 只设计指标 | Business -> Metrics |
| 已有指标，需要 SQL | Metrics -> SQL |
| 普通数据诊断 | Business -> Metrics -> SQL -> Insight -> Review |
| 需要图表 | 在 Insight 后增加 Visualization |
| 正式报告 | 在 Review 后增加 Report |
| 已有完整结果，只需复核 | Review |

路线约束：

- 问题和业务范围已经明确时允许跳过 Business。
- 已有用户确认的指标时允许跳过 Metrics，但必须注册并绑定其原始文件和哈希。
- 没有执行结果时 Insight 只能提出假设，不能输出真实数值结论。
- 涉及真实数据库、归因判断或正式交付时，Review 不得跳过。
- Report 和 Visualization 不再是普通分析的默认必选角色。

### 10.6 七 Agent 调度与有限并行

七个正式角色全部保留，不因为个人模式而删除、合并或永久改写角色职责。角色数量与运行时并发数量分开管理：

- 默认同时运行一个 Agent。
- 主要阶段按照 Business、Metrics、SQL、Insight、Visualization、Review、Report 的依赖关系串行。
- 完整分析可以运行全部七个角色，但不同时启动七个 Agent。
- 复杂阶段在存在互不依赖的子问题时，最多同时启动两个 Agent；任务完成后再合并为一个阶段结果。
- 同一阶段没有独立子问题时，不为了并行而拆分任务。

允许的阶段内并行例子：

- 两个不同用户分群分别分析。
- 两个独立原因假设分别验证。
- 数据质量检查和行为趋势检查分别进行。
- 两套互不依赖的图表方案分别提出。

并行约束：

1. 并行 Agent 必须读取同一份冻结输入和证据哈希。
2. 每个分支保存独立的分支标识、原始回答、验证结果和证据引用。
3. 分支之间不能把未经验证的结论互相当作事实。
4. 结果冲突必须展示给用户或 Review，不能由根任务静默选择一个。
5. 用户确认合并后的阶段报告，不需要分别确认两个临时分支。
6. SQL 执行、结果发布和最终报告发布不因并行而绕过原有审批。
7. 分支结果安全保存后关闭 Agent 会话，七个角色配置和正式证据继续保留。

阶段报告仍只整理当前阶段的 Agent 内容，不由根任务补写新的业务事实。公共运行字段继续沿用当前程序和现有产物结构，不新增规范化文件、双哈希或转换记录层。

### 10.7 准确信息交接的不可削弱约束

当前使用的“不可变、哈希绑定的结构化交接 + 确定性程序校验 + 独立 Review”继续作为两种模式的共同底座。

必须保留：

1. JSON 是 Agent 间交接的系统事实来源，Markdown 只用于用户阅读。
2. 下游只读取已批准的上游 JSON、真实数据文件及其准确 SHA-256，不通过复制上游文字报告完成交接。
3. 每个证据引用必须解析到已注册产物和具体选择位置；自由文本中的“根据数据”不算证据。
4. SQL Agent 只提出 SQL。真实执行由根运行时完成，并生成绑定 SQL、数据源指纹、执行限制、结果文件和结果哈希的查询清单。
5. 指标必须具有稳定 `metric_id`、版本、公式、粒度、时间窗口、适用人群和字段依赖；SQL 必须明确映射支持和不支持的指标。
6. Review 必须读取不可变输入包，覆盖批准决策、指标血缘、查询清单、结果、数据画像、图表和已知断点。
7. 上游输入、路线、指标、SQL 或结果发生变化时，依赖旧哈希的下游产物必须失效。
8. 原始 Agent 响应、Agent ID、配置哈希、批准记录和最终采用产物必须保留。

准确性边界也必须向用户说明：哈希能证明内容未被修改，不能证明业务定义和原始数据库天然正确；Review 是独立检查，不是数学上的绝对正确保证。因此系统对事实的最低要求是可解析证据，对结论的最低要求是证据与推理明确分离。

### 10.8 一次完整前置校验和有限修复

将格式、角色合同、证据引用、输入哈希、指标映射、Review 输入包和运行上下文校验合并到正式登记之前。

目标流程：

`Agent 输出 -> 完整预校验 -> 同一 Agent 会话修正一次 -> 保存原始响应和回执 -> 正式登记`

要求：

- 一次返回完整错误清单，不让 Agent 逐项试错。
- 自动格式修复最多一次，运行时必须记录自动修复次数。
- 用户主动修改不计入自动修复预算，但必须生成新修订。
- 修复失败后停止当前阶段，不启动下游 Agent。
- 正式登记仍执行最终防篡改检查，不能因为前置校验而取消。

### 10.9 上下文和控制命令精简

目标是把新建或恢复运行的公共必读规则从 40,532 字符降低到 15,000 字符以内。

- `SKILL.md` 只保留模式选择、关键安全规则、主流程和按需参考入口。
- Metrics、SQL、数据库、图表、报告、安装和迁移资料仅在相关阶段读取。
- 恢复时优先读取紧凑运行摘要，不默认把完整状态和事件日志送入模型上下文。
- 控制命令默认只返回状态、当前阶段、变化、风险、待确认项和下一合法动作。
- 完整状态、完整证据和技术附录继续存盘，只在诊断或用户要求时读取。
- Review 可读取完整证据索引，但不应重复加载与当前结论无关的阶段报告正文。

### 10.10 个人模式状态和 Agent 生命周期

个人模式保留一个运行状态文件、审批记录、指标版本、SQL 与结果哈希、中断恢复和单写者文件锁。

个人模式不新增低风险状态的完整哈希链、非查询阶段执行租约、完整状态默认输出或可由批准产物重新推导的重复元数据；具体停止项
统一见 10.11。

查询执行保护、结果原子发布、关键产物哈希和严格模式审计链继续保留。

指标工作台区分草稿和批准版本：草稿允许用户直接反复修改；用户确认后才登记为新的不可变指标版本。日常修改不额外生成重复
的中间交接文件。

Agent 生命周期统一为：

`按需启动 -> 返回结果 -> 同会话最多修正一次 -> 保存原始响应和回执 -> 关闭执行会话`

七个角色配置和全部批准证据长期保留；完成的执行会话及时关闭，避免占用并发线程。重大业务变化、回退或输入版本变化应启动新的隔离尝试，不复用带有旧上下文的会话。

### 10.11 明确停止建设的内容

以下内容不进入个人版后续任务：

- 公共字段规范化、规范化产物和双哈希。
- 核心依赖与图表依赖拆分，以及独立 core 环境磁盘测试。
- 非查询阶段的执行租约和低风险状态的完整哈希链扩展。
- 通过多层 manifest 重复保存同一份阶段信息。
- 继续扩展复杂合同迁移体系；只保持现有旧运行读取能力。
- 通用 DAG 编排器、Agent 模型自动评分、RAG、向量数据库和复杂管理后台。
- 增加新的固定 Agent 角色，或把现有七个角色合并删除。

### 10.13 验收标准

个人模式完成需要同时满足：

1. 七个 Agent 配置全部保留，完整分析按主要阶段串行运行七个角色。
2. 默认并发为 1；复杂阶段的独立子问题最多并发 2，不同时启动七个 Agent。
3. 个人模式使用最短路线；Visualization 和 Report 只有在路线需要时调用。
4. `key-gates` 只保留路线、指标、准确查询执行和正式交付等必要确认。
5. 公共必读规则不超过 15,000 字符，其余资料按阶段加载。
6. Agent 自动格式修正最多一次，并能区分用户主动修订。
7. 控制命令默认不输出完整运行状态。
8. 个人模式和严格模式使用相同的证据解析、SQL 只读校验、查询清单和过期失效规则。
9. 人为篡改任一批准 JSON、SQL、结果或证据哈希都必须被阻止。
10. 没有真实结果的 Insight 只能输出假设；没有可解析证据的 Report 结论不能发布。
11. 已有 v1.2 运行仍可读取、审计和按显式迁移规则处理。
12. 新模式必须有日常短路线、完整七角色路线、阶段内双 Agent 并行、真实数据库路线、回退恢复和严格模式兼容测试。

1. 先完成确定性路线选择和宽泛问题澄清，保留七个角色配置。

4. 保持前置校验、指标草稿编辑和准确证据交接，不增加规范化中间层。
5. 简化个人模式事件和非查询租约，保留查询安全边界。
6. 按职责拆分 `runctl.py`，只做代码组织，不新增运行层。
7. 完成自动测试后，按用户指令逐步运行真实 Agent 对照，不一次启动大规模评测。
